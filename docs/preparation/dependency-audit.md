# Fullscreen and Game Mode dependency audit

This is a source audit, not a claim of upstream acceptance. It compares the accepted fork at `86d6c80624413f895806afcdd8ff7f93b059d759` with freshly recorded YAAGL upstream `fc56d843461a313fdc5c19af2a2a47eaf8f2f6ac`. Source links below pin those revisions. The user now reports that the optimized `build/launch-hashing-20261001/Yaagl OS.app` works exactly as intended; its reported executable source is `5f1cff960aa82e2538f08caf4022299bfb92efc5`. That acceptance supersedes requests for further tuning, but does not establish that an extracted native patch has identical behavior. No cursor, Retina, resolution or performance policy change is proposed here.

## What remains with FPS entirely absent

The claim of functional independence is supported by source: [launch lines 395–425][launch] select `prepareR2Wine({fps:false, fullscreen:true})` and `launchGameDisabledProgram`; no `launchFpsGame` call follows. Fullscreen-only replaces the three Mac driver components. Game Mode additionally selects the **plain routing** ntdll and ordinary/host loaders. The window registry helper never starts a game or FPS worker. An upstream extraction need not even import `admitFpsLaunch`.

The stronger phrase “fullscreen-only always retains original ntdll” needs qualification: [recipe lines 120–130][recipe] accept either original **or already R2-corrected** input and preserve whichever is supplied when `applyR2` is false. On the pinned public original input, no R2 transform is applied. This byte admission lives in `native/wine-r2/delta.json`, but is a shared runtime identity mechanism, not proof that R2 is needed. Split it out rather than accepting arbitrary Wine bytes.

Direct and Steam entry still use upstream's `cmd /c config.bat` or signed `steam.exe` route. Native fullscreen alone neither changes loader identity nor needs `WINELOADER`, Game Mode, host assets, ntdll changes, FPS target/control, worker/bridge, R2, controller support, launch timing, Sophon changes or a DXMT source patch. DXMT-specific qualification in the fork is a tested-runtime restriction, not evidence that the Cocoa change intrinsically requires DXMT.

## Lifecycle: existing upstream support and precise gaps

Upstream has useful building blocks: [Wine methods][up-wine] already bind a loader and prefix; `wine.exec` is a foreground command; `wineserver -w` exists; [termination hooks][up-neu] support normal close veto; [task queue][up-queue] serializes a launch in one UI; startup `init` precedes queued actions. These are enough to avoid importing the fork's entire ownership architecture, but they do **not** provide its guarantees without changes:

1. [Upstream `exec2` lines 39–85][up-neu] awaits `spawnProcess` before registering its event handler, so a fast-exit event can be missed; output buffers are reset inside each event. `waitUntilServerOff` uses that same event path. The smallest feature-scoped fix is to use existing foreground `exec`/`execCommand` for the game command, registry helpers and `wineserver -w`, with the captured loader/prefix/environment. This mirrors accepted `Wine.exec2(..., requestBound=true)` and its foreground wait. Alternatively repair/test `exec2` as a separate general bug fix. Transport failure still means completion is uncertain; retain recovery state.
2. [Upstream HK4E lines 166–210][up-launch] wait and restore registry only on the success path, log a caught failure, then remove files/revert patches. Preparation occurs before that `try`. The enabled feature needs a `try/finally` covering mutation onward, drain on success **and failure**, restore retry, and a pending marker retained on uncertainty. A `finally` containing asynchronous cleanup must finish without yielded progress being mistaken for completed cleanup.
3. The task queue is not a lifetime guard and does not reserve a launch synchronously before all awaited work. Register a request guard before preparation; keep it through helper completion, Wine drain and restore. Use `addTerminationHook` for normal close and await completion on forced relaunch/shutdown: upstream forced shutdown ignores a false return. Preserve errors instead of calling the queue's fatal exit while restoration remains unresolved. The exact UI wording and the fork's message overhaul are unnecessary.
4. Run recovery before admitting the enabled launch or changing its runtime. Record original prefix/loader/environment and raw snapshots; drain that context first. Runtime B must retain the private runtime until recovery can execute and finish. A recorded/discovered error must not clear the pending pointer. A per-UI queue is not cross-process locking; multiple launcher instances sharing a prefix require explicit exclusion or documented prevention before concurrent transaction support can be claimed.

For the smaller fullscreen integration, cancellation before game creation can simply stop preparation and restore. While the game is live, decline normal launcher close and wait for game/Wine completion. That removes any requirement for FPS jobs, global process matching, `killall`, or a new general cancellation supervisor. Forced OS termination is handled by startup recovery, not a promise that JavaScript will run after death.

## Exact registry scope and recovery

The [helper][registry] mutates only these HKCU values, selected by mask:

| Value | When written | First fullscreen integration |
| --- | --- | --- |
| `Software\Wine\AppDefaults\GenshinImpact.exe\Mac Driver\AllowFixedSizeFullscreen` (or `YuanShen.exe`) | Fullscreen enabled; `REG_SZ "Y"`. | Essential opt-in for this registry-based design. Snapshot absent/type/raw bytes before write; restore after drain. |
| `Software\miHoYo\Genshin Impact\Screenmanager Is Fullscreen mode_h3981298716` (CN key `原神`) | Fullscreen enabled **or** explicit/remembered size supplied; `REG_DWORD 0`. | Needed to launch windowed for the green-button flow. Restore the original raw value, including absence. |
| `…\Screenmanager Resolution Width_h182942802`, `…\Screenmanager Resolution Height_h2627697771` | Nonzero explicit/remembered dimensions. | Not needed merely to enable native fullscreen. When explicit upstream resolution also writes these in the enabled transaction, snapshot them together before either writer runs; prevent the old delete-on-exit path from overwriting the restored preimage. No new default dimensions or memory policy. |

`RetinaMode`, `LeftCommandIsCtrl`, HDR, DXMT configuration and cursor policy are outside this transaction's mutation set. Reuse existing settings behavior. New keys/ancestors created for this transaction may be deleted only if still empty; unrelated values/subkeys survive. The accepted helper flushes an immutable snapshot before apply and refuses restore when an applied transaction's snapshot is absent. Simplifying registry persistence to `.reg` strings would lose arbitrary raw types/absence unless that serialization is separately proven equivalent.

Both runtime distribution approaches still need rollback and startup recovery **if YAAGL makes these temporary changes**. A maintained driver does not erase registry persistence. A durable user-controlled app-specific Wine preference could avoid rollback of that one driver value, but changes product policy and still does not solve temporary game fullscreen-mode/size overrides; it is not assumed here.

## Existing-plan findings that must not be overstated

- The [prior plan][prior] correctly separates FPS and cross-launch memory; source confirms both. Its “minimal verified composition adapter” is needed under B, not A for fullscreen.
- The Game Mode app metadata alone is insufficient: source preserves resolved child identity, inherited Wine context and same PID. A fixed app around the launcher or forwarding parent is not an equivalent extraction.
- Shipping the native patch removes fullscreen sidecar replacement and per-launch copying under A. **It does not automatically remove Game Mode private-runtime coupling:** [routing.h][routing] requires an adjacent fixed request pathname and host path; [prepare-r2.pl][recipe] selects one regional sealed host in that private copy. A shared runtime needs a new safe external request location and host-selection contract; blindly writing those files into installed Wine is not acceptable.
- The historical [Game Mode report][gm-report] includes explicit OS “Game Mode On” observations on one Apple M4/macOS 26.6.2 Global/Steam configuration and later corrections to stale R2 build evidence. Those observations are more than plist evidence, but do not qualify every eligible OS, CN, direct launch or the new extraction. Metadata/log text is never activation evidence.
- Current live acceptance concerns the accepted application. Test counts, matching version strings, old runtime hashes or matching exported symbols cannot establish an exact publisher rebuild, auxiliary-window correctness or review readiness.
