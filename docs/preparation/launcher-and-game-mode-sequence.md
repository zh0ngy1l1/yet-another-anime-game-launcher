# Distribution choice and later launcher contributions

The recommended target is **A: a maintained runtime that includes the opt-in fullscreen patch**. That gives the runtime owner responsibility for its Cocoa driver and removes per-launch native replacement from YAAGL. This is a proposal contingent on an agreed owner and an actually published, qualified build; no such new release is assumed available. The concrete native prototype is reviewable independently. Until a capability exists, upstream launcher code must not advertise a functioning fullscreen setting for existing unpatched runtime tags.

All launcher work starts from YAAGL `fc56d843461a313fdc5c19af2a2a47eaf8f2f6ac`, not the accepted fork history. [The source audit](dependency-audit.md) identifies the exact reusable behavior, upstream API gaps and source links. This document proposes a later sequence; it does not implement Game Mode or change the accepted application.

## A and B are materially different contributions

| Decision | A — maintained Wine includes native changes | B — YAAGL ships matched replacement components/private runtime |
| --- | --- | --- |
| Fullscreen source | Generic `dlls/winemac.drv/{cocoa_window.h,cocoa_window.m,macdrv.h,macdrv_cocoa.h,macdrv_main.c,window.c}` patch plus tests, submitted to the agreed Wine/overlay source owner. | Same source patch and provenance, built by a launcher-associated native maintainer; replacing binaries does not eliminate source contribution or license obligations. |
| Launcher changed files | HK4E default-off configuration, settings/locales, `program-launch-game.ts`, bounded registry transaction/recovery, capability data in `src/wine/distro.ts`/Wine object, minimum lifetime guard in existing execution/close/startup paths. A narrow registry helper may still require packaging. | A's launcher changes plus runtime-root/environment injection in `createWine`, neutral composition/staging module, native assets/manifests, private-runtime receipt and disposal/recovery, package/source/license verification. Do not port FPS-named modules wholesale. |
| Runtime release changes | Source owner rebases/builds driver; distributor publishes signed matched native and PE modules with exact source/build identity and a stable capability contract. Distribution repository can host release work without being the source-patch destination. | YAAGL native owner builds compatible Mach-O/PE trio; Game Mode later adds plain routing ntdll, ordinary loader, sealed host bundle(s). Launcher release must deliver code, manifest and assets atomically. |
| Supported runtime policy | Explicit verified release capability, not a guessed minimum version. Default-off in Wine; no change to other distributions. Existing `11.0`/`11.8`/CrossOver choices do not acquire capability from their names. | Exact supported input/module identities and architecture. The fork currently pins the `11.0-dxmt-signed-with-patches` input, rejects other inputs, and uses APFS cloning. Retain those restrictions for B unless replacement validation demonstrates broader support. |
| Update compatibility | Runtime upgrade must preserve/revalidate option semantics and publish a capability revision. Do not replace Wine while its old loader/server or registry recovery is needed. Launcher resources need not embed driver hashes, but any bundled helper still needs matching version/integrity. | Every Wine/overlay update can invalidate replacement ABI, signatures, assets or routing. Resource-only launcher updates must either include matching native assets and source/notices or reject incompatibility/use complete-bundle updates. Do not import the fork's replacement build pipeline merely to enforce that contract. |
| Private runtime | Not needed for fullscreen when shipped driver is immutable and option is app-scoped. No whole-runtime hash/clone or sidecar copy on launch. | Needed by this approach to avoid mutating installed/runtime-in-use files. A smaller safe runtime layout is an investigation, not established here. Exact compatible files, source immutability, no unsafe shared mutable files, retained completion and cleanup are mandatory; repeated whole-tree hashing is not intrinsically mandatory. |
| Game Mode consequence | Current routing cannot simply be copied into a shared runtime: request is bound to adjacent `yaagl-game-mode.request`, and preparation chooses one regional host at a fixed path. Agree safe external request lookup, concurrent-prefix behavior, fixed sealed host choice and compatible ntdll binding before claiming A removes private copies for Game Mode. | Existing request binding and fixed per-copy host layout are feasible, but carry per-launch preparation and native update responsibilities. Plain routing variant must remain independent of FPS/R2. |
| Ongoing owner | Wine/overlay owner for Cocoa behavior, distributor for signed builds and release provenance, YAAGL for preference/transaction and integration checks. No agreement yet. | YAAGL contributor/native owner must maintain builds, source delivery, compatibility pins, signatures, host identity, preparation and upgrade/recovery cases across every supported runtime. This is larger than a settings PR. |

B is a viable preparation/fallback design because the accepted fork already ships matched assets; it does not require pretending an unpublished Wine release exists. It is a poor default upstream proposal without explicit ownership of native releases. If maintainers prefer B, extract a small neutral adapter and qualify it separately. Neither approach changes Retina, render resolution, keyboard mappings, FPS limits or game cursor handling.

## Minimum YAAGL fullscreen design under A

1. Add a default-false HK4E option with green-button instructions. The Wine capability record must come from a known qualified runtime release; no optimistic fallback for arbitrary Wine. If unavailable, retain the saved preference, show an inactive explanation and launch through the ordinary upstream path with no feature mutations. Do not switch runtimes silently. This deliberately differs from the fork's fail-before-preparation admission policy to preserve the requested upstream unavailable behavior.
2. Capture the selected Wine context and acquire the feature transaction guard before mutation. Use ordinary upstream direct/Steam launch commands and their existing environment/settings. Avoid any FPS import. Read raw preimages for app-specific `AllowFixedSizeFullscreen` and HK4E windowed mode; include explicit resolution values only if the existing custom-resolution path will change them in this transaction. Persist the recovery record and immutable snapshot before apply.
3. Reuse existing foreground execution for helpers/game command and the matching `wineserver -w`. Put setup/game failure and success through a common `finally` path that drains Wine, restores raw values, drains helper Wine activity, clears the durable pointer last, then releases admission. An unconfirmed wait or failed restore retains state and blocks conflicting work. Add the small close/startup adapter described in the audit; no progress yields that can truncate cleanup.
4. Enter fullscreen only through AppKit's ordinary green button. The native patch owns the frame during entry/exit; the launcher does not inspect Spaces or write a window-memory file. Leave cross-launch position/size memory out. Other clients and feature-disabled launches keep their upstream behavior; a pre-existing pending feature recovery must still be honored even after the user disables the preference.
5. Package the small registry helper/source/manifest if that implementation is chosen; use the existing build process. The helper can be synchronous and narrow; the fork's `observe`/memory commands, ownership supervisor, R2 input manifest and runtime-copy layer are not prerequisites under A. A different registry API/serialization is acceptable only if raw types, absent values and durable retry are preserved.

These changes are a coherent small integration, not literally “a checkbox plus registry write.” Safe lifetime and recovery cannot be deferred after shipping the setting. The dependency audit's upstream fast-exit/abnormal-completion findings justify the prerequisite instead of assuming a large fork supervisor is necessary.

## Game Mode requirements beyond fullscreen

The current implementation's boundary is independently inspectable in [loader.c][loader], [routing.h][routing], [resolved-image.patch][resolved], [metadata][metadata] and [asset recipe][gm-build]. A later extraction must answer each item:

Its recorded source is Wine `db11d0fe6a169c457e23d007e20404643d067aa8` (11.0) with `riverfog7/macports-wine` overlay `0d029255bce8f2f4ac47a1984b59ba82e09d9829`. `loader/main.c` and `dlls/ntdll/unix/process.c` are Wine source changes; `yaagl/anime-game-wine` is a distribution/build coordination target, not automatically their source-review destination. Rebase any later Game Mode extraction onto the maintainer-agreed source baseline and rebuild before claiming compatibility with another release.

- **Actual game process:** `main` calls `yaagl_route` before Wine initialization; ordinary loader uses `execv(host, argv)` and the host enters `__wine_main` in that same PID. Preserve argv[0], inherited Wine socket/handles, cwd, reservations, environment and loader lifetime. An eligible parent does not substitute for the actual game host.
- **Resolved child:** the `NtCreateUserProcess` path supplies the opened image's Unix name to `spawn_process`; each native child overwrites the routing value, including empty for builtins. Retain tests where command-line text pretends to be a different executable. Simply setting `WINELOADER` on the outer process does not establish inner child routing in this Wine baseline.
- **Plain variant:** build and qualify only routing ntdll/loader without `native/wine-r2` or FPS bridge/worker. The fork's optional R2 composition is a separate downstream combination, not an upstream prerequisite. Keep the signed Steam shim, registry/setup tools, wineboot and unrelated children on their ordinary identities.
- **Request binding:** capture canonical selected executable, prefix and file identity; bind compatible ntdll and expected host; reject missing/mismatched assets before a wrong identity runs. This is launch admission, not an isolation boundary against the user. For A, redesign external request location/host selection first; the current fixed adjacent file cannot support arbitrary shared-runtime requests safely.
- **Identity/presentation:** maintain a stable agreed bundle identifier (fork uses `com.zh0ngy1l1.yaagl.hk4e-game`), games category and `LSSupportsGameMode`; embedded/external plists must agree, and no `LSUIElement`. Decide region naming and whether to ship the currently attributed official shortcut icon or other permitted artwork. Do not rename a sealed bundle per launch. Identifier changes can change OS remembered preferences; assign ownership before release.
- **Native release:** choose supported architecture/OS/SDK, signing and notarization policy, source/license delivery and rebuild owner. Existing host derives from LGPL Wine loader; include notices, modifications and reproducible procedure, without asserting byte-identical SDK builds. Ad-hoc component signing in the fork is evidence of its current package policy, not a maintainer commitment to distribute that way.
- **OS observation:** `admitGameMode` checks Apple Silicon/macOS 14+ and the qualified runtime, but saving a setting, seeing a host identifier or `LSSupportsGameMode=true` only demonstrates eligibility. Verify macOS actually says “Game Mode On” during gameplay in native fullscreen. Do not infer performance improvement or use Gaming Focus/overlay visibility alone as proof.

## Reviewable order and dependencies

| Order | Proposed contribution | Depends on / completion evidence |
| --- | --- | --- |
| 1 | Generic opt-in fixed-window native fullscreen patch and focused fixtures in the agreed Wine/overlay source repository. | Recorded source baseline; minimal extraction; disabled behavior and transitions; honest auxiliary-window comparison. No YAAGL/Game Mode transport. |
| 2 | Native runtime build/release capability contract (A), or separately reviewed verified composition/package adapter (B). | Source review and named build owner. Pin an actual published qualified release before enabled launcher support; no fabricated version/hash. |
| 3 | YAAGL foreground completion/launch transaction prerequisite. | Upstream API gap reproducers, `finally` drain, normal close/forced-relaunch guard, immutable snapshots and startup recovery. Can be reviewed while native release is pending. Keep disabled paths narrow; unrelated launch fixes remain separate. |
| 4 | YAAGL HK4E default-off fullscreen setting + capability + registry transaction wiring. | 1–3; FPS entirely absent; direct/Steam, abnormal completion and recovery checks. Same-session native restoration only. |
| 5 | Optional cross-launch window memory proposal. | Independent product decision; do not make 4 depend on it. Geometry attribution/Retina/resolution precedence would require a separate design. |
| 6 | Game Mode resolved-child/loader/host source and plain routing build. | Stable fullscreen behavior and agreed native ownership; A needs external-request/shared-runtime design. Review independently from launcher setting and R2. |
| 7 | YAAGL Game Mode setting, host admission, request binding, assets and package/update checks. | 4 and 6; direct/Steam without FPS; observed OS activation on the claimed host/configuration; helper identities preserved. |

No PR or maintainer message is sent at this stage. Sequence may be split differently by maintainers; source ownership, policy and release support are unresolved decisions, not published requirements.

## Later launcher acceptance matrix

| Area | Required evidence before launcher submission |
| --- | --- |
| Off/unavailable | No new runtime, helper, registry or environment changes when off/unavailable; same direct/Steam command and existing resolution/Retina behavior. Preference stays saved; no runtime switch. Recover a prior pending enabled session before admitting any conflicting work. |
| FPS absent | Direct and signed Steam-child routes with fullscreen on/off, and later Game Mode on/off. No FPS module/worker/R2 artifact needed. Global and CN admitted executable matches; real-game qualification clearly distinguished from synthetic fixtures. |
| Normal completion | Exit windowed and in native fullscreen; helper completion and matching Wine drain precede restoration/disposal; original raw registry values restored; repeated launch works. Same-session window geometry belongs to native tests. |
| Abnormal completion | Nonzero command exit, helper failure, game crash, command transport uncertainty, close/relaunch during preparation/cleanup; no early runtime disposal or false success. Cancel before creation never resumes into launch. |
| Interruption/recovery | Stop launcher after durable save, after partial apply, during game, after restore marker, before pointer deletion. Restart uses original prefix/runtime, no interrupted memory promotion; missing/corrupt snapshot blocks unsafe restoration; retry is idempotent. Disposable fixture prefixes only. |
| Updates | Runtime replacement or launcher resource update cannot mix incompatible code/native assets or remove a retained runtime needed for recovery. A validates runtime capability; B rejects mismatched modules/host/ntdll and updates matching package contents together. |
| Game Mode identity | Resolved game vs misleading argv; helpers and Steam ordinary; actual native game PID/path/bundle agree; Foundation identity + native fullscreen + explicit OS activation. Treat activation and performance as separate observations. |

Apple Silicon/macOS 26.6.2 Global/Steam historical gameplay and the user's accepted candidate are the available documented game evidence. Other supported-version claims, CN gameplay, different hardware/displays and the generic extraction's complete acceptance matrix remain unproven unless the assessment's new fixture report explicitly records them. Do not turn capability checks or historical test totals into broad compatibility claims.
